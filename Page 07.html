Section 02 · Vertex AI MLOps Pipeline

Eight-step training pipeline. Applied uniformly across all five models.

Every model passes through the same Vertex AI Pipelines topology[cite: 9]. Promotion is gated on metric thresholds[cite: 9]. Model Cards are auto-generated from training run metadata[cite: 9]. High-risk models under EU AI Act require a manual gate before full deployment[cite: 9].

01

Data Validation

Great Expectations Pipeline Gate

Great Expectations schema validation runs against the Feature Store snapshot before any training computation begins[cite: 9]. If schema drift is detected against the registered feature contract, the pipeline fails immediately — no training job is submitted, no compute is wasted, and an alert is raised to the ML Engineer on-call via PagerDuty[cite: 9].

02

Feature Engineering

Vertex AI Feature Store

All feature transformations are executed with lineage metadata written to the Feature Store at each step[cite: 9]. Transformation logic is versioned alongside the feature group — ensuring that every model version can be exactly reproduced from a point-in-time feature snapshot, satisfying EU AI Act data provenance requirements[cite: 9].

03

Distributed Model Training

Vertex AI Training Vertex AI Vizier

Distributed training on Vertex AI Training with hyperparameter tuning via Vertex AI Vizier[cite: 9]. Each training run generates a full experiment lineage record: hyperparameter configuration, training data snapshot hash, framework version, and compute configuration — all captured in the Vertex AI Experiments registry before the model artifact is produced[cite: 9].

04

Model Evaluation

Champion Gate

Evaluation metrics are computed on the held-out evaluation set and compared to the registered champion model performance[cite: 9]. Promotion to the next pipeline step is gated on metric thresholds — MAPE for DemandIQ, AUC-ROC for classifiers[cite: 9]. A challenger model that does not improve on the champion is blocked from registration[cite: 9].

05

Model Card Generation

Automated

Model Card is auto-populated from training run metadata, evaluation results, and bias analysis computed over demographic slices of the evaluation set[cite: 9]. Sections include: intended use, training data provenance, evaluation results, bias analysis, ethical considerations, EU AI Act classification, regulatory obligations, and version history[cite: 9]. No manual authoring required[cite: 9].

06

Model Registration

Vertex AI Model Registry

Model artifact, Model Card, and SHAP explainer artifact are registered together as a versioned bundle in Vertex AI Model Registry[cite: 9]. Each version carries a regulatory metadata tag set: EU AI Act risk class, applicable regulatory obligations, Model Card reference, and the identity of the training run that produced it[cite: 9].

07

Canary Deployment

10% Traffic Split

The challenger model receives 10% of live inference traffic alongside the champion[cite: 9]. Champion/challenger performance comparison runs over a 48-hour observation window[cite: 9]. Both models log SHAP explanations to the audit trail during this period, enabling side-by-side explainability comparison as well as metric comparison[cite: 9]. Canary window / retraining conflict protocol: For SupplierSentinel (weekly retraining cadence), if a drift event fires during an active 48-hour canary window, the canary is immediately paused, the champion serves 100% traffic, and the retraining pipeline takes priority[cite: 9]. The canary observation window restarts fresh once the new challenger clears the champion gate[cite: 9]. This conflict protocol is encoded as a pipeline condition, not an operational procedure[cite: 9].

08

Full Promotion

Conditional Promote — Metrics + Manual Gate

Promotion to 100% traffic is conditional on two gates passing in sequence[cite: 9]. First, canary metrics must hold against champion thresholds over the full observation window[cite: 9]. Second, because all five models are EU AI Act High-Risk, full promotion requires explicit manual approval from the designated ML Engineer and a compliance sign-off record before traffic shift[cite: 9]. Neither gate can be bypassed[cite: 9]. Rollback capability is preserved: if post-promotion metrics degrade within the 72-hour monitoring window, automated rollback to the previous champion is triggered and logged to the immutable audit trail[cite: 9].

⚖ EU AI Act Article 9 — Human oversight gate required before full deployment of any high-risk model[cite: 9] ↩ Rollback — automated revert to champion within 72h window if post-promotion performance degrades[cite: 9]

Section 03 · Drift Detection & Retraining Triggers

Three drift thresholds. One automated response chain.

Feature drift, prediction drift, and performance drift are monitored continuously via Vertex AI Model Monitoring and Cloud Monitoring custom metrics[cite: 9]. Every drift event is timestamped, logged with the model version reference, and routed through PagerDuty before any retraining trigger fires[cite: 9].

Feature Drift

Threshold PSI > 0.2 on any top-5 feature[cite: 9]
Detection Method Vertex AI Model Monitoring — feature distribution monitoring[cite: 9]
Response Alert → PagerDuty → ML Engineer on-call[cite: 9]. Investigation required before retraining decision[cite: 9].
Audit Logging Drift event written to immutable audit log with timestamp and model version reference[cite: 9].

Prediction Drift

Threshold KL divergence > 0.1 on output distribution[cite: 9]
Detection Method Cloud Monitoring custom metrics — prediction distribution tracking per endpoint[cite: 9]
Response Alert + mandatory investigation[cite: 9]. Distinguishes between data shift and model degradation before triggering retraining[cite: 9].
Audit Logging Drift event written to audit log[cite: 9]. Investigation outcome recorded before any retraining pipeline is initiated[cite: 9].

Performance Drift

DemandIQ Threshold MAPE degrades >5pp against registered champion baseline[cite: 9]
Classifier Threshold AUC-ROC drops >0.05 against registered champion baseline[cite: 9]
Response Automatic retraining pipeline trigger[cite: 9]. Champion remains serving until challenger is promoted through full pipeline[cite: 9].

⚖ GDPR Article 17 — Audit Log Retention & Right to Erasure

SHAP explanation artifacts written to the audit log at inference time include input feature values[cite: 9]. Where any feature value is derived from personal data (e.g. named contact data within supplier records, news sentiment attributed to identifiable individuals), the following controls apply[cite: 9]:

  • ·Retention policy: Audit log entries are retained for 7 years to satisfy MDR and ISO 13485 traceability obligations[cite: 9]. SHAP artifacts containing personal data are pseudonymised at write time — the supplier entity ID is stored; raw personal identifiers are not written to the audit log[cite: 9].
  • ·Erasure conflict resolution: Where a GDPR Art. 17 erasure request conflicts with a mandatory MDR retention obligation, the MDR obligation takes precedence under GDPR Art. 17(3)(b) (processing necessary for compliance with a legal obligation)[cite: 9]. The DPO is notified of each such conflict and maintains a register[cite: 9].
  • ·Immutability scope: "Immutable audit log" means append-only with cryptographic integrity verification — not that erasure is technically impossible[cite: 9]. The pseudonymisation layer ensures erasure of the personal identifier is possible without invalidating the audit record integrity[cite: 9].

Section 05 · Feature Store Design

Three shared feature groups. No feature duplication across models.

Feature groups are designed to be shared across models — eliminating training/serving skew and ensuring that a feature value computed once is consumed consistently by every model that depends on it[cite: 9]. Feature freshness SLOs are enforced by the ingestion pipeline, not just measured[cite: 9]. Access to feature groups is governed by IAM role-based access control — models and agents consume features via service accounts with least-privilege scope[cite: 9]. GDPR data minimisation applies: no feature group stores personal data beyond what is necessary for the declared model purpose; supplier_features contains entity-level scores only, not the underlying personal data records from which scores are derived[cite: 9].

Section 06 · Robustness, Rollback & GDPR Article 22

EU AI Act Article 15. Accuracy, robustness, and cybersecurity — throughout the lifecycle.

Article 15 requires that high-risk AI systems achieve appropriate levels of accuracy, robustness, and cybersecurity across their operational lifetime — not just at deployment[cite: 9]. This section specifies the robustness controls applied uniformly to all five models, the rollback procedure triggered when a promoted model degrades, and the GDPR Article 22 position for the two models whose outputs most directly affect third-party decisions[cite: 9].

Out-of-Distribution Detection

Trigger Condition Any inference request with ≥1 feature value outside ±3σ of training distribution[cite: 9]
Automated Response Request flagged[cite: 9]. Prediction returned with ood_flag=true[cite: 9]. Downstream agent routes to HITL — no autonomous action taken on OOD inferences[cite: 9].
Audit Log Contract OOD event logged with feature vector, model version, and routing decision[cite: 9].

Adversarial & Malformed Input Handling

Inference Gate Great Expectations schema validation runs at inference — same contract as training pipeline Step 01[cite: 9]. Payload errors reject records before reaching endpoints[cite: 9].
Endpoint Security All model endpoints are private, accessible only within VPC Service Controls perimeter[cite: 9]. No public inference endpoint[cite: 9]. IAP enforced for human-facing HITL surfaces[cite: 9].
Threat Model Posture Model endpoints are not externally reachable[cite: 9]. Primary attack surface is internal — covered by VPC perimeter, service account least-privilege, and Cloud Armor on API Gateway[cite: 9].

Graceful Degradation Under Feature Unavailability

Tolerance Parameters Models tolerate absence of ≤2 non-critical features[cite: 9]. Missing features are imputed using training-set median[cite: 9]. Imputation is flagged in SHAP output[cite: 9].
Critical Feature Unavailability If a critical feature (defined per model in Feature Store metadata) is unavailable, inference is blocked and escalated to ML Engineer on-call[cite: 9]. No prediction with unknown reliability is served[cite: 9].
Classification Boundary Critical features per model are designated at registration time and versioned in Vertex AI Model Registry alongside the model artifact[cite: 9].

Rollback Procedure — All Five Models

Rollback Trigger Post-promotion performance metrics degrade beyond threshold within 72-hour monitoring window, OR a compliance issue is identified in the promoted model[cite: 9].
Rollback SLA Champion model restored to 100% traffic within ≤15 minutes of rollback decision[cite: 9]. Traffic shift is automated via Vertex AI endpoint split update[cite: 9].
Rollback Authority Automated rollback: triggered by metric threshold breach[cite: 9]. Manual rollback: any designated ML Engineer or Compliance Officer can trigger via ITSM ticket — no change freeze required[cite: 9].
Audit Log Contract Rollback event written to immutable audit log: timestamp, triggered-by identity, reason code, previous champion version, and post-rollback verification metric[cite: 9]. EU AI Act Article 9 rollback record[cite: 9].
